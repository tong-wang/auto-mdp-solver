# FNV Domain — fresh-newsvendor sequential ordering under MMFE

Place `N` sequential orders at rising unit cost while a martingale demand signal
is progressively revealed (Heath & Jackson 1994, MMFE). Demand realizes once at
the horizon and is sold against cumulative inventory; the objective is expected
profit.

Reference paper: Tong Wang, Atalay Atasu, Mümin Kurtuluş (2012), "A
Multiordering Newsvendor Model with Dynamic Forecast Evolution",
*Manufacturing & Service Operations Management* **14**(3), 472–484,
[doi:10.1287/msom.1120.0387](https://doi.org/10.1287/msom.1120.0387).
© 2012 INFORMS, which holds copyright — **the PDF is not redistributed
here**; read it via the DOI or your library. What this case reimplements
from it are mathematical facts, each attributed at the call site: the
Proposition 2 policy form (`fnv_benchmark_prop2.py`) and the Corollary 1
inequality (`fnv_benchmark_myopic.py`). The structural claim the §14
readback tests is the paper's own — that the optimal base-stock level
depends on the information state linearly (additive MMFE) or log-linearly
(multiplicative).

Generated by the **auto-mdp-solver** skill from `fnv_schema.json`. The IR half
was contributed first (v0.8.0, demoted from `examples/` for shipping no
train/eval pair); this folder completes it with the solve leg, the benchmarks,
the campaign record and the §14 readback. See `CLAUDE.md` before changing
anything here.

## MDP structure

**Scenario parameters** (`FnvScenario`):
- `N` — number of ordering periods (default 3)
- `T` — time location of the last ordering epoch, `0 < T < 1`
- `stdev` — total demand standard deviation
- `lamb` — per-period ordering cost increment (`c_n = c1 + (n-1)*lamb`)
- `mu` — mean terminal demand / log-scale parameter

**Demand process** (both modes share the same information process):
- a-MMFE: `D = mu + I[N+1]`
- m-MMFE: `D = exp(mu + I[N+1])` (`E[D] = exp(mu + stdev²/2)`)

`I[n]` is the cumulative normal demand signal revealed up to epoch `tau[n]`.
Increments are path-independent and keyed under **seed scheme v2** (§6.3) as
`[period, source_id, 1, episode_seed, seed_salt]` — leaf-first, so the trailing
word is always `seed_salt >= 1`.

**Observation** (`observation_mode="vec"`): `[stdev, T, lamb, period, inventory, information]`

**Action** (`action_mode="box"`): continuous order quantity in `[0, mu + 5*stdev]`
(a-MMFE) or `[0, exp(mu + 5*stdev)]` (m-MMFE).

**Reward** (`reward_mode`):
- `"profit"` — `-ordering_cost` each step, `+revenue` at the terminal period
- `"regret"` — same, minus `profit_max` (the clairvoyant optimum) at terminal

## Scenarios vs grids

These are different things and live in different registries (§5.5–§5.6).
A **scenario** is one world; a **grid** is an experiment-design set — the
generality target a generalist policy is trained to cover.

`SCENARIOS` (`fnv_scenarios.py`):

| Name | Description |
|---|---|
| `simple` | fixed additive params (stdev=0.1, T=0.9, lamb=0.1); sanity-check / fast training |

`GRIDS` (`fnv_grids.py`) — **separate leaderboards, never compared**:

| Name | Cells | Description |
|---|---|---|
| `FNV-aMMFE` | 540 | additive; stdev∈{0.05…0.3} × T(9) × lamb(10) |
| `FNV-mMMFE` | 540 | multiplicative; stdev∈{0.1…0.6} × T(9) × lamb(10) |

Training takes `GRIDS[name].as_sampler()` (one cell drawn per episode, on the v2
meta key); evaluation enumerates cells, one row each. A grid is never passed
where a scenario source belongs.

## The solve leg, in order

The terminal checkpoint is **never** the deliverable (§8.6). Training produces
~20 checkpoints; a post-hoc screen ranks them; the protocol block confirms.

```bash
# 1. train (runs to budget, no early stopping)
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python fnv_ppo_train.py -s FNV-aMMFE

# 2. screen ~20 checkpoints on 2048 CRN seeds disjoint from the protocol block
python fnv_select.py results/FNV-aMMFE/PPO_<run>

# 3. confirm the top-k on the evidence-grade block; this TSV is the leaderboard
python fnv_ppo_eval.py --model-path results/FNV-aMMFE/PPO_<run>/checkpoints/<ckpt>.zip \
    -s FNV-aMMFE --n-seeds 8192
```

Screen scores rank only and are never quoted. The two seed blocks are disjoint
by construction (`SCREEN_SEED_BASE = 1_000_000` vs `PROTOCOL_SEED_BASE = 0`).

Training and evaluation scenarios are **decoupled**: a model trained on `simple`
can be evaluated on the full `FNV-aMMFE` grid, or vice versa.

## The optimal-policy benchmark — two independent solvers

The optimal policy is order-up-to `S_n = mu + I + b_n` (a-MMFE) /
`exp(mu + I + b_n)` (m-MMFE). Two solvers compute the offsets `b_1..b_N` by
different routes, and both write the same TSV that `fnv_benchmark_dp_eval.py`
consumes:

```bash
# (a) value-function DP — collapses (inventory, information) to z = x - (mu + I)
python fnv_benchmark_dp.py -s FNV-aMMFE --self-test

# (b) the PAPER's algorithm — Proposition 2's one-dimensional recursion
python fnv_benchmark_prop2.py -s FNV-aMMFE --check-invariants --cross-check

python fnv_benchmark_dp_eval.py --dp-solutions results/FNV-aMMFE/benchmark/prop2/FNV-aMMFE.txt -s FNV-aMMFE
```

`fnv_benchmark_prop2.py` implements Wang, Atasu & Kurtuluş (2012) Proposition 2
directly: `b_n` is the root of `g_n(b_n) = 0`, where

```
g_N(y) = r·Φ̄(y/σ_{N+1}) − c_N                                              (7)
g_n(y) = ∫_{−∞}^{(y−b_{n+1})/σ_{n+1}} g_{n+1}(y − σ_{n+1}ζ) dΦ(ζ) + c_{n+1} − c_n   (6)
```

Because the offsets are independent of the information state, this is a set of
one-dimensional equations solved **off-line** — the paper's main computational
point, and much cheaper than re-solving a 2-D DP per state.

**Three gates back these numbers.**

| gate | what it proves | result |
|---|---|---|
| `--self-test` (DP) | the recursion reproduces the exact newsvendor last period, `b_N = σ_{N+1}Φ⁻¹(1−c_N/r)` | ≤ 4.5e-04 |
| `--check-invariants` (Prop 2) | Corollary 1's `b_n ≤ b̂_n`, and that `b_n` is MMFE-mode-independent (eqs 6–7 never reference the mode) | −3.9e-09 margin; |Δ| exactly 0 |
| `--cross-check` (§1.2) | the two solvers, derived independently, land on the same offsets | max 2.6e-03 over all 540 cells (mean 3e-04) |
| scored policies | the offsets' *behaviour* agrees, not just their values | max 2.4e-05 profit over 540 cells — ~180× below the eval's own SE (4.3e-03) |

## Leaderboard — `FNV-aMMFE`

Protocol tier: 540 cells × 2048 CRN seeds, seed block 0…2047, identical for
every arm, so the Δ column is a **paired** per-cell comparison. Grid-mean
profit weights each cell equally.

| arm | what it is | profit | Δ vs optimum | % of bar |
|---|---|---|---|---|
| `prop2` | **optimum** — the paper's Prop 2 recursion (`--reference`) | **0.888334** | — | — |
| `dp` | **the same optimum**, by an independent value-function solver | **0.888334** | −0.0000001 | 0.00% |
| PPO, best of 9 | best confirmed checkpoint (L0 seed2, step 1.4M) | 0.886428 | −0.001907 ± 0.000077 | −0.21% |
| `myopic` | **must-beat baseline** — safety stocks that ignore future ordering (`--baseline`) | 0.878686 | −0.009649 ± 0.000517 | −1.09% |

`dp` and `prop2` are two independent derivations of the *same* optimal policy,
so they are one bar, not two arms — they agree to a paired mean of 1e-07
(max 2.4e-05 over 540 cells) against an eval SE of 0.0043. Both are listed
because their agreement **is** the §1.2 second-implementation gate: if they ever
diverge, the bar itself is in question and no arm below it means anything.

The learned policy sits **0.21% under the exact optimum** and beats the myopic
baseline by +0.0077 ± 0.0005 paired. All nine trained models clear the
baseline; the spread across them is 0.8825–0.8864.

Two caveats that the single number hides:

- The gap to the optimum is small because the **profit landscape is flat**, not
  because the policy is nearly right — it misses one of the three ordering
  opportunities entirely. See `INTERPRET.md`.
- `myopic` is a deliberately weak arm (Corollary 1 guarantees `b_n ≤ b̂_n`, so
  it over-orders early by construction). Beating it is a floor check, not a
  result.

## The readback (§14)

FNV ships a DP reference, so the **anchored** form is required.

```bash
python fnv_policy_probe.py --model-path <ckpt> -s FNV-aMMFE
python fnv_plot_policy.py --probe-dir results/FNV-aMMFE/PPO_<run>/probe -s FNV-aMMFE
```

The probe reports, per period: the raw action surface, an order-up-to
**flatness** statistic (0 = exact base-stock), the recovered `b_hat` against the
DP's `b_n`, action agreement, and feature-sensitivity slopes. It then scores the
fitted rule as a policy on the same CRN block and reports the trio
reference / fitted rule / raw net with paired Δs — the fitted rule can beat the
net it was read from, in which case `N` numbers are the shippable artifact.

Figures follow §14.3: the committed static SVG lands in `fnv/figures/`, the
interactive HTML in `results/{scenario}/figures/` (gitignored). The location
split *is* the gitignore boundary.

## Output folder structure

Exactly the spec §8.4 tree — no level between `{scenario}/` and `{run_name}/`,
and one `results/` root (never a `results_L0/`-style variant per experiment;
the **run name** carries the config, which is why an L0 control and an L1 run
sit side by side under the same scenario):

```
results/
  {scenario}/                          # e.g. simple/, FNV-aMMFE/
    {run_name}/                        # PPO_<ts>_default, PPO_<ts>_lr0.0003_..._normobsFalse
      {scenario_name}_ppo.zip          # terminal model (NOT the deliverable)
      vecnormalize.pkl                 # VecNormalize running stats (if used)
      {scenario_name}_ppo_args.txt     # CLI args + SB3 version + T_bar basis
      train.log                        # teed console of the training run
      eval.log                         # teed console of the eval run
      checkpoints/                     # ~20 periodic checkpoints (§8.6)
      screen.tsv                       # fnv_select.py ranking (never quoted)
      probe/                           # §14.1 raw measurements: action surfaces, sweeps
      interpret/                       # §14 conclusions: fitted form, agreement, verdict
      monitor_{rank}.monitor.csv       # SB3 Monitor, one per env
      PPO_1/                           # TensorBoard event files
      ppo_eval_{eval_scenario}.tsv     # protocol-tier PPO eval
    benchmark/
      {method}/                        # dp/, prop2/, myopic/
        {scenario}.txt                 # that method's offsets b_1..b_N
      benchmark_{method}_eval_{scenario}.tsv   # protocol-tier benchmark eval
      benchmark_{method}.log           # its teed console
    figures/                           # interactive HTML (gitignored)
  insights/                            # across-run / across-policy comparisons
    fitted-rule-vs-benchmark/          # §14.2 trio scores (not about one model)
figures/                               # committed static SVG
```

### Output TSV columns

Both protocol-tier eval scripts share one schema, so arms are directly
comparable and `mdp_gates` can read them (it takes the first `*_mean` column):

```
stdev  T  lamb  n_seeds  profit_mean  profit_se  regret_mean  regret_se  profit_var  semivar_d  semivar_u
```

`--per-seed-out` additionally dumps per-seed profits, which is what a paired Δ
between two arms needs.

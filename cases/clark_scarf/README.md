# clark_scarf — serial multi-echelon inventory (Clark & Scarf 1960)

A single product moves down a serial chain of stocking points. Level 1 is a
retailer facing Poisson demand; level *N* buys from an unlimited outside
supplier. Each period every link dispatches **simultaneously** — one shipment
quantity per link — each clipped to what its source installation physically
holds. Shipments take `leadtime` periods to land and cannot be recalled. Unmet
demand backlogs. Minimize expected discounted cost (β = 0.95) over 50 periods.

Source: Andrew J. Clark and Herbert Scarf, *Optimal Policies for a Multi-Echelon
Inventory Problem*, Management Science 6(4), 1960 (read from the 2004 reprint,
Management Science 50(12S), pp. 1782–1790). The model is §2–§3, generalized to
N levels as §3's scheme `[N] → … → [2] → [1]` describes.

Generated by the **auto-mdp-solver** skill from `clark_scarf_schema.json`.
See `CLAUDE.md` for the operating brief and `ESCALATION.md` for the campaign.

## The question this domain exists to answer

Echelon stock is an artifact of the paper's *analysis*, not something a warehouse
manager sees. **Given only raw installation stock, does an RL policy rediscover
the echelon aggregation Clark & Scarf prove is the right coordinate system?**

The two observation modes are related by an **invertible** map, so they carry
identical information. This is a test of **representation, not information** —
not whether the agent can uncover something hidden, but whether the coordinate
system must be handed over or whether the network builds it itself. An MLP can
express a cumulative sum (a lower-triangular matrix of ones), so a `raw`
shortfall would be an optimization finding, not an impossibility.

| obs mode | what the agent sees |
|---|---|
| `raw` | physical stock at each installation, plus what is in flight toward it |
| `echelon` | the same numbers under the paper's coordinates — running sums applied **component-wise** to stock and to in-flight stock separately |

The component-wise part is load-bearing. A single running sum over their total
would be genuinely lossy at `leadtime = 2` and would turn the experiment into a
test of information. §3's own state is `C_n(x₁, w₁, x₂)` — in-transit `w₁` is
carried *separately* from echelon stock, for exactly this reason.

### The answers — `n3_l2_p09`, campaign closed

**1. How does RL compare with the existing solutions?** The trained policy
reaches **989.07** against a **verified-optimal** DP at 982.36 — **100.69% of
the optimum**, a headroom of 6.71 — and beats the best heuristic
(echelon base-stock, 1021.13) by **32.06**. Against the §8.6 L0 control at
1193.36, the pipeline's derivation plus one tuning round is worth **204.29**.
The DP's optimality is not assumed from Theorems 1–2: it was checked against a
brute-force DP over the full joint state, gap 0.000000 (#E1).

**2. Must the echelon coordinates be handed over?** **No — and the reason is
that the network builds them.** Two independent findings, and they compose:

| | finding |
|---|---|
| **outcome** | The price of generality is **−0.55 ± 0.14** at the derived centre — inside the measured 1.57 training-seed floor — and the point estimate falls to **−0.0014** once each branch is tuned separately, with four independently tuned artifacts (two per observation mode) landing within **0.027** of one another. The tuned ± is eval-paired on one training seed per arm, so the *seed-backed* leg is the L1 measurement; both agree on zero (#E4, #E7) |
| **mechanism** | The `raw`-trained policy **is** a base-stock rule on echelon aggregates. Where the availability clip is slack the implied order-up-to level takes **exactly one value per echelon — 37, 59, 79 — identical to the DP's critical numbers, with interquartile spread 0.0** over ~36,000 decisions. Hold the echelon position fixed and redistribute the raw split: the decision is unchanged at echelons 2–3 (#E8) |

So the coordinate system does not have to be supplied, because a policy given
only raw installation stock **reconstructs it and then applies Clark & Scarf's
own critical numbers**. Those two halves could have come apart — a policy that
matched on score while remaining structurally unreadable would have been the
weaker, more common result. See `INTERPRET.md` for the readback and its limits.

## Usage

Gates run from the **parent** of `clark_scarf/`; everything else from inside it.

```bash
# gates
python -m mdp_ir clark_scarf/clark_scarf_schema.json
python -m mdp_conformance clark_scarf
python -m mdp_ir.laws clark_scarf
python -m mdp_ir.differential clark_scarf/clark_scarf_schema.json --episodes 40 --all-instances
pytest clark_scarf

# layer smoke tests
python clark_scarf_mdp.py       # fixed-policy episodes across chain lengths
python clark_scarf_gym.py       # random episodes, every mode + the coordinate-change check

# benchmarks (8192 shared seeds)
python clark_scarf_benchmark_dp.py     -s n3_l2_p09      # solve the critical-number table
python clark_scarf_benchmark_dp_eval.py     -s n3_l2_p09 --n-seeds 8192
python clark_scarf_benchmark_echelon_eval.py -s n3_l2_p09 --n-seeds 8192
python clark_scarf_benchmark_local_eval.py   -s n3_l2_p09 --n-seeds 8192
python clark_scarf_benchmark_random_eval.py -s n3_l2_p09 --n-seeds 8192

# is the decomposition really optimal here?
python clark_scarf_dp_exactness.py

# train (record eval is DETERMINISTIC — see CLAUDE.md Traps)
OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 python clark_scarf_ppo_train.py \
    -s n3_l2_p09 -o raw -a ship_discrete --level L1
python clark_scarf_ppo_eval.py -s n3_l2_p09 \
    --model-path results/n3_l2_p09/<run>/n3_l2_p09_ppo.zip \
    --paired-with results/n3_l2_p09/benchmark/benchmark_dp_eval_n3_l2_p09_perseed.npy

# what did it learn?
python clark_scarf_policy_probe.py -s n3_l2_p09 --model-path results/n3_l2_p09/<run>/n3_l2_p09_ppo.zip

# the deployable policy: replay it against the raw MDP loop, no gym (spec §12)
python clark_scarf_policy.py --model-path results/n3_l2_p09/<run>/n3_l2_p09_ppo.zip \
    --vecnorm-path results/n3_l2_p09/<run>/vecnormalize.pkl -s n3_l2_p09 --episodes 512
```

### Using the trained policy

```python
from clark_scarf_policy import ClarkScarfPolicy

pol = ClarkScarfPolicy("…/n3_l2_p09_ppo.zip", scenario="n3_l2_p09")
ship = pol.act(obs)          # one shipment quantity per link, already clipped
```

`obs` is the vector `clark_scarf_gym.observation()` produces —
`[period/horizon, stock(n), in-flight blocks(n × (L−1))]`, described in full in
that module's docstring. It must be the **pre-order, post-arrival** state; a
post-dispatch state produces a plausible but wrong shipment. VecNormalize
statistics are mandatory at inference, not optional: the network was trained on
normalized inputs. The wrapper reproduces `clark_scarf_ppo_eval.py` to the
digit — both score **996.103846** over seeds `0…511`.

`results/` is gitignored; every number below reproduces from these commands.

## Results — `n3_l2_p09` (3 echelons, lead time 2, shortage 9)

Discounted total cost, **minimized**. All arms replay the same CRN seed block
`0…8191`, so differences are pairwise.

| arm | method | role | cost | SE | vs DP | what it knows |
|---|---|---|---|---|---|---|
| **DP — Clark–Scarf** | `dp` | **exact** | **982.36** | ±1.19 | — | echelon idea **+** Theorem 2's induced penalty |
| `echelon_bs` | `echelon` | feasible | 1021.13 | ±0.86 | +3.9% | the echelon idea, no decomposition |
| `local` base-stock | `local` | feasible | 1120.92 | — | +14.1% | pre-1960 single-installation practice |
| random | `random` | feasible | 37069.12 | ±48.95 | +3673% | — |
| **PPO L2(hp)** — `target_discrete` + `raw` | `ppo` | feasible | **989.07** | ±1.19 (eval) | **+0.69%** | nothing — learned from stock |
| PPO L2(hp) — `target_discrete` + `echelon` | `ppo` | feasible | 989.07 | ±1.19 (eval) | +0.69% | the echelon transform, handed over |
| PPO L1 — `target_discrete` + `raw` | `ppo` | feasible | 992.54 | ±0.6 (seed) | +1.0% | nothing |
| PPO L0 (control) | `ppo` | feasible | 1193.36 | ±7.3 (seed) | +21.5% | nothing |

**The two L2(hp) rows are the campaign's headline, and their equality is the
point.** Four independently tuned artifacts — two per observation mode,
different learning rates, rollout lengths and architectures — land within
**0.027** of each other at 8192 CRN seeds. Paired per-seed, `raw − echelon` is
**−0.0014** (eval-paired ± 0.0123, one training seed per arm): given each branch its own hyperparameters,
handing the policy Clark & Scarf's coordinates buys nothing measurable. The
L1 rows show the same comparison before tuning, at −0.55 ± 0.14.

The L1 figures are **two-seed means**; the L2(hp) figures are single training
seeds, so the −3.47 / −4.02 gain is ≈2σ on the training-seed scale rather than
the ≈2.2 the 1.57 floor alone would suggest. See `ESCALATION.md` #E7.


**`role`** places an arm relative to the optimum, sense-free: with
`objective.sense = minimize`, `relaxed ≽ opt` (unattainable — none here),
`exact = opt`, `feasible ≼ opt`. A `feasible` arm scoring better than the
`exact` one is impossible; if it ever does, the eval, the bound or the
simulator is wrong. `method` is the artifact name — the file
`clark_scarf_benchmark_{method}.py` and the results directory
`results/{scenario}/benchmark/{method}/`. This column was the interim home for
role while the IR had nowhere to put it; upstream #23 — filed from this
campaign — shipped the root-level `benchmarks` block in **v0.8.5**, and all
four are **now declared there**: `dp=exact`, `echelon`/`local`/`random`
`=feasible`. So the ordering above is enforced rather than read:
`mdp_gates --ir` places the DP as a reference and would fail a feasible arm
that beat it. The declaration is root-level and moved neither fingerprint.

The `dp` entry carries `tolerance = 0.001` and a `basis` recording why: the
decomposition is exact as an *algorithm*, but its Poisson pmf is truncated at
dropped mass < 1e-9 per period while the simulator's sampler is not, so the
bar may be optimistic by at most ~1e-4 over the horizon. That is the caveat
`role` cannot carry — role is about the algorithm's logic, `basis` about its
numerics.

The ladder decomposes cleanly: `local → echelon_bs` = **99.8 units**, the price
of the echelon idea itself; `echelon_bs → DP` = **38.8 units**, the price of
Theorem 2's induced penalty.

**Gate classification.** `random` and `local` are the **baselines** an RL arm
must beat. `echelon_bs` and `dp` are **references**, reported but never gated
against: both are handed the echelon insight, and gating an agent that has to
*discover* the structure against a benchmark that was *given* it is the wrong
experiment (`ESCALATION.md` #E2).

**The DP row is a verified optimum, not an assumption.** Theorems 1–2 are a claim
about the paper's model; `clark_scarf_dp_exactness.py` checks it against a
brute-force DP over the full joint state on `verify_tiny` and finds a gap of
**0.000000**. One documented caveat: the DP truncates the Poisson pmf at a high
quantile while the simulator does not (mass < 1e-9), so "% of optimal" carries
that qualifier.

**Stage-4 gate: PASS.** L1 beats `random` (z = 717) and `local` (z = 81.4).
It also lands **below `echelon_bs`** — an agent given only raw installation
stock, and no inventory theory, beats the heuristic handed Clark & Scarf's
echelon insight — and within **2.8%** of the verified optimum, with no
escalation beyond the spec's own §8.6 derivation. The derivation itself is
worth ~15% (L1 − L0 = −183.6, z = −160).

**Pass `--sense minimize`** to `mdp_gates`; it defaults to `maximize`, which on a
cost column inverts every verdict.

## Empirical findings

These are established by the benchmark suite, the gates, and reading the paper
against the implementation — independent of any RL run.

### The exact DP was 30% suboptimal, and looked entirely convincing

The first implementation charged each decision against demand over the `L`
transit periods. Cost is actually assessed on the **end-of-period** state, one
further demand draw on — the periodic-review *"lead time plus one"*. Subtly, the
two terms need **different** risk periods: cost is realized at end of period
`s+L` (`D_{L+1}`), but availability binds at the *decision* point of `s+L`
(`D_L`).

The wrong table was plausible in every respect — monotone critical numbers
increasing up the chain, a sensible time-varying profile collapsing to "don't
order" at the horizon end, and `ȳ₁ = 26` matching an independently computed
newsvendor fractile. Every gate stayed green. Only the brute-force comparison
caught it. Fixed: gap → 0.000000, targets `[26,48,69] → [37,59,79]`. Guarded by
`test_clark_scarf_decomposition_is_exactly_optimal`.

### The "naive" benchmark rung was not naive

An echelon base-stock heuristic reads like a simple baseline, but it is **handed
the paper's central insight** — that the right state variable is echelon
inventory position, covering the *cumulative* distance to the customer. Nobody
reaches that without the analysis; §1 of the paper describes the prior
literature as concerned with "a *single installation*". The genuinely
traditional rung is `local`: each installation runs its own single-location
base-stock over its **own** lead time, scoring 1120.92.

Lesson: classify a benchmark by **what knowledge it is given**, not by how
simple its code looks, and keep theory-informed arms in `--reference`.

### In-transit stock belongs to the echelon above

Assumption 3: a level's costs cover stock at that level plus stock "at a lower
level **or in transit to a lower level**". *Lower* is operative — stock in
transit **to** level *j* belongs to echelon *j+1* and is charged its **source's**
rate until it lands. A unit in flight to the retailer costs the same as one
sitting at the depot; shipping downstream is what *starts* the higher charge,
and it starts on arrival, not on dispatch.

The first frozen model charged it to the destination, double-charging pipeline
stock. Caught by reading the assumption against the implementation — **the
differential passed bit-exact both before and after**, because it proves the
interpreter and the domain agree, not that they agree on the right model.

### Chain length does not subsume lead time

An extra **installation** is a *discretionary buffer* — units sit there and the
policy re-decides each period whether to move them on. An extra period of **lead
time** is *committed flow* — once dispatched, a unit arrives on schedule and no
decision can touch it. Same delay, different control. Both are swept as
independent axes.

### Policy-structure readback

The crowned `raw` policy recovers the paper's rule *exactly* where the
availability clip is slack: implied order-up-to 37 / 59 / 79, IQR **0.0**,
matching the DP's critical numbers to the unit. Agreement with the optimal
action is 95.4% / 90.4% / 84.0%, degrading up the chain with a **positive**
bias (+0.41 → +1.38) — it over-orders upstream, the cheap direction of error
here, and that residual is where the 6.71 gap to the bar lives.

The discriminating test is invariance: hold the echelon position fixed and
vary how the same total is split across installations and pipelines. Spread is
**0.00** at echelon 3 and 0.43 at echelon 2 — the split is irrelevant to the
decision, which is what "found the aggregation" means. Echelon 1 keeps a small
residual (0.75) that is *defensible rather than a defect*: level 1 faces demand
this period, so its on-hand-versus-in-transit split genuinely matters in a way
echelon position does not capture.

## Scenario set

The swept sets below are **experiment design**, not the model: the model
admits any `leadtime` >= 1 and any `n_echelons` >= 2 (restatement §Model
envelope), and the rendering carries **no cap on either**: `pipe` declares
`length: ["n_echelons", "leadtime"]` and the `ship` decision `dim:
"n_echelons"`, so an instance renders exactly the shape it selects and any
`(N, L)` is representable (ESCALATION §IR-CHANGELOG F7 and F9, which removed
the `LEADTIME_CAP = 4` of F3 and then `N_LEVELS_MAX = 4`). The theory itself
is declared in the schema's `mdp.model` and checked by `mdp_conformance`'s
`model.boundary` (F6), which PASSes with every width derived from its
reference.

Three swept axes — `n_echelons` ∈ {2,3,4}, `leadtime` ∈ {1,2},
`p_short` ∈ {4,9,19} — for **18 cells**. Each is its own trained policy and its
own leaderboard: chain length and lead time change the observation and action
width, and `p_short` changes the cost scale, so **no score may be compared
across cells**. The two observation modes *within* a cell are comparable — that
comparison is the point.

This pass targets `n3_l2_p09`. Full rationale in `clark_scarf.scenarios.md`.
